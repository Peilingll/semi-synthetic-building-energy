# 2026-06-09 — Stage 1: ResNet-50 full fine-tune

## Model (`src/stage1/models.py::ResNet50FT`)

- `timm.create_model("resnet50", pretrained=True)` → 2048-d → masked mean-pool
  → trunk (256) → 3 heads (type/year/floors), same shape as the DINOv2 path
- **Packed forward**: only valid images go through the backbone
  (`images[valid_mask]` → backbone → scatter → pool). The dataset pads every
  building to 8 slots; with ~4.7 images/building on average, ~40% of slots are
  all-black padding that, in train mode, would corrupt the BatchNorm batch
  statistics. Packing fixes this and saves ~40% compute. (DINOv2 path unchanged:
  its frozen+eval backbone makes padding harmless.)
- **Discriminative lr**: backbone 1e-4 / trunk+heads 5e-4, norm+bias excluded
  from weight decay (4 param groups).

## OOM debugging (8 GB WDDM GPU)

The main engineering difficulty. Recorded in full for the later Swin-T run.

**Root cause** (reached by elimination — not batch size, not a specific fold,
not external apps): `vram_peak_mb` (4.2 GB at batch 12) under-reports because it
only counts allocated memory, not fragmentation or the backward-pass spike. The
**packed batch is variable-size** — batch 12 worst case is 12 buildings × 8
images = 96 images backpropagated at once — and on Windows WDDM the OS-managed
GPU memory plus accumulated fragmentation means that, after 2-3 hours, the 96-
image spike occasionally hits the 8 GB ceiling. Folds 0/1/2 completing at batch
12 was luck (no early shuffle hit the worst batch while memory was tight).

A separate, earlier bug: validation did not wrap the forward in `no_grad`, so a
full-fine-tune fp32 val batch peaked at 13.5 GB and spilled into WDDM shared
memory (epochs dragged to 1000s+). Fixed → 3.9 GB, 165s/epoch. Harmless on the
frozen-backbone DINOv2 path, fatal here.

**Fix (fault tolerance, not setting-gambling):**
1. `torch.cuda.empty_cache()` per epoch (commit `344a7e0`) — fights fragmentation
2. `garbage_collection_threshold:0.8` — earlier allocator reclaim
3. **One fold per process** (`--fold N`) — a single fold is <1 h, low OOM odds;
   if one fold dies only that one is re-run
4. **Unified batch 8** — worst batch 64 images, stable ~3.1 GB peak

Result: all 5 folds completed at batch 8, peaks 3083-3195 MB, zero OOM.
Hold-out eval also needs `--batch-size 8` (the default 32 → 256-image worst
batch OOMs).

## Interpretation

**DINOv2 frozen and ResNet-50 ft are effectively tied** (overlapping CIs):
ResNet edges type_acc (0.915 vs 0.901), DINOv2 edges macro_f1 (0.520 vs 0.492)
and year/floors; period_acc near-identical. Full fine-tuning an ImageNet
ResNet-50 matches a frozen self-supervised DINOv2 backbone with a light head —
supporting the spec's question of whether frozen SSL features rival supervised
fine-tuning, here at much lower training cost (DINOv2 frozen peaks 3.1 GB, no
backbone backprop).

**Methodological note**: the head-lr fix (review point 2) makes this comparison
valid. Under the spec's single lr, ResNet's randomly initialised head would
underfit and macro_f1 would spuriously collapse, falsely concluding "frozen SSL
beats full ft". Methods must report the discriminative lr.

Residual type weakness (MFH f1=0, n=12; SFH 0.356, canal-house confusion)
mirrors the VLM and stems from the 88%-AB hold-out imbalance, not a model flaw.

## Spec deviations (for methods chapter)

1. discriminative lr (backbone 1e-4 / head 5e-4), not single lr
2. batch 8 (8 GB GPU constraint; spec leaves batch unspecified)
3. checkpoint selection by val macro-F1, not val loss (see DINOv2 F4 loss figure)
4. packed forward (BN correctness)
