# 2026.05.01 — Phase C Full-Delft OpenFACADES Run

## Goal

Run OpenFACADES on the entire Delft residential area to produce per-building
street-view image candidates for downstream VLM inference. Building on Phase A
(Zurich smoke test) and Phase B (single 600×600 m bbox over 8 ground-truth
buildings), Phase C splits Delft into a residential grid and runs each cell
independently.

## Pipeline changes vs. Phase B

1. **OpenFACADES `run.py` patch (Patch #3)** — added `--stages {1,2-6,all}`
   flag so the pipeline can be split into footprint download (stage 1) and
   image extraction (stages 2-6). Documented in
   `doc_processed/log/openfacades_patches.md`.
2. **BAG-residential pre-filter** — between stage 1 and stage 2-6 the wrapper
   applies a centroid-containment spatial join against
   `bag_3dbag_ep_joined.parquet ∩ residential_tabula_matched.parquet` and
   overwrites `footprint.geojson` with the residential subset only. Cuts ~75%
   of non-residential buildings from GroundingDINO inference (Phase B observed
   1,811 → 423 ratio).
3. **Grid orchestrator** `src/phase_c_grid_runner.py` — builds a 600×600 m grid
   over the BAG residential bounds with 50 m overlap, drops cells that contain
   zero residential centroids, sorts the rest by residential density (high
   first), and runs each cell in two subprocess calls (`--stages=1` then
   `--stages=2-6`). Outputs go to `data/openfacades_output/phase_c_delft_grid/`
   (folder isolated from Phase A/B).
4. **`.env` workflow** — added `.env` (gitignored) for `MAPILLARY_API_KEY`
   together with `.env.example`. Wrapper parses the file directly so the
   subprocess gets the token without relying on shell exports.

based on assumed Mapillary coverage and turned out to be unrealistic for
Delft residential streets.

## Failure analysis (19 cells)

| Root cause                              | Cells | Retry can recover? |
|-----------------------------------------|-------|--------------------|
| AoV select = 0 (Mapillary panoramas exist in cell but not within isovist of any residential) | 5 | No — true coverage limit |
| Network timeout (Mapillary `graph.mapillary.com` or Overpass) | 5 | Yes — re-run cell |
| OpenFACADES bug `KeyError: 'building_floor'` in `harmonizer.py:137` (column missing when no OSM building has the tag) | 1 | Needs upstream patch |
| Other stage 2-6 RC=1 (likely also intermittent network, log truncated by progress display) | 8 | Likely yes |

So **at most 5 / 19 failures are an actual Mapillary coverage limit**; the
other 14 are recoverable with retry or a small upstream patch. Worst-case
"true" coverage if every recoverable cell had been saved is still bounded by
the Mapillary footprint in those cells — likely +50-80 buildings, lifting
coverage to roughly 7-10 %, still far below the 70 % target.

## Key findings

1. **The ≥ 70 % Mapillary coverage assumption in the original spec was wrong
   for Delft.** Even discounting recoverable failures, Mapillary panoramas in
   residential neighbourhoods cover a small minority of buildings. This is the
   same observation Phase B made on 8 ground-truth buildings (0/8) but now
   quantified across the entire municipality (≈ 5-10 %).
2. **The `building_id ↔ pand_id` spatial-join strategy continues to work
   well.** All 7 successful cells produced clean mappings; the merged
   footprint dedup is unambiguous because OSM/Overture IDs are globally
   unique.
3. **The two-stage `--stages` patch is operationally correct.** No cell
   reported a schema mismatch between filtered footprint and stage 2-6, no
   isolation issues against Phase A/B folders.
4. **Non-residential filtering paid off.** Cells dropped 70-90 % of buildings
   at the filter step (e.g. cell_0007: 1,758 panos → AoV=70 → 287 residential
   → 631 final images). GroundingDINO ran on a much smaller universe than a
   no-filter run would have.
5. **Wall-time of 3 h beat the 1.5–2.5 day estimate from the spec.** Reason:
   the BAG residential bounds (used to derive the grid) are ≪ Delft
   administrative bounds — only 26 residential cells materialised, not the
   150-200 estimated in the spec.

## Open issues / next-step options

1. **Fix `harmonizer.py:137` KeyError.** Add a guard for missing
   `building_floor` column. One-line patch, cleans up cell_0000 (and possibly
   other small cells where no OSM building has `building:levels`).
2. **Re-run only failed cells (idempotent resume).** `progress.json` already
   has retry support; running the wrapper a second time will pick up the 19
   failures. With network jitter typically being the cause, expect a non-zero
   recovery rate.
3. **Decide on coverage strategy.** Three options:
   - **A.** Accept ~5–10 % coverage and proceed to VLM inference on the 1,164
     images / 163 buildings. Frame the low-coverage number as a thesis
     finding ("Mapillary-only methods cover ~5 % of NL residential buildings
     in Delft").
   - **B.** Increase OpenFACADES isovist buffer from 30 m → 100 m to recover
     more buildings per pano. Requires editing
     `OpenFACADES/src/openfacades/streetview/aovcalculator.py`. Expected gain:
     unclear; tighter buffers were the spec's quality-vs-coverage trade-off.
   - **C.** Add Google Street View Static API as a fallback for cells where
     Mapillary failed. ~$25 for 3,300 buildings; ToS prohibits redistributing
     the dataset.
4. **Document the spec's 70 % assumption as outdated.** Update
   `openfacades_integration.md` §1 acceptance criterion to reflect Phase C's
   measurement, and add Phase C to the §Phase A/B/C progress section.
