# 2026.05.17 — Phase C Extension to Utrecht: Smoke + Mapillary Coverage Warning

## Goal

Replicate the Delft Phase C OpenFacades pipeline on Utrecht / Rotterdam /
Amsterdam to support cross-city ablation in the thesis. This pass runs a
Utrecht smoke (1–3 cells) to validate the multi-city plumbing and quantify
Mapillary 360° coverage.

## Code changes

### 1. `src/phase_c_grid_runner.py` — `--city` flag for multi-city runs

New argument `--city <name>`. When provided, the runner loads
`configs/<city>.yaml` and overrides default-valued paths:
- `--bag-geom` ← `data_paths.joined_output`
- `--residential` ← `data_paths.tabula_output`
- `--output-root` ← `data/openfacades_output/phase_c_<city>_grid/`

Behavior with no `--city` flag is identical to the pre-existing Delft default
(backwards compatible — Phase C Delft progress.json untouched).

```
python -m src.phase_c_grid_runner --city utrecht --build-grid-only
python -m src.phase_c_grid_runner --city utrecht --max-cells 1
python -m src.phase_c_grid_runner --city utrecht
```

### 2. OpenFacades Patch #5 — empty Mapillary panorama guard

`D:/ITBE/Thesis/OpenFACADES/run.py` `prepare_mly_metadata()` now returns `None`
when MLYDownloader skips writing `pids_urls.csv` (zero 360° panoramas matched
in the bbox). `main()` checks the sentinel and exits cleanly instead of
crashing on `FileNotFoundError` inside `process_metadata()`. Documented in
`doc_processed/log/openfacades_patches.md` (Patch #5).

### 3. Runner status taxonomy: `no_pano_coverage` vs `failed`

`run_one_cell()` outcomes:
- `rc=0` + `select.csv` exists → `done`
- `rc=0` + `pids_urls.csv` missing → `no_pano_coverage` (no retry)
- anything else → `failed` (retry up to MAX_RETRIES_PER_CELL = 2)

Resume mode skips `done`, `no_pano_coverage`, and `skipped_after_filter`.
`verify_openfacades_patches()` adds a Patch #5 signature check.

## Finding: Utrecht Mapillary 360° coverage ≪ Delft

Comparison vs. Delft Phase C:
- Delft: 26 residential cells, 9 `done` (with pano imagery), 17 `failed`
  (in retrospect, many of these were probably the same `no_pano_coverage` case
  that Patch #5 now distinguishes).
- Utrecht: top-2 highest-density cells confirmed at 0 panos.

OpenFacades defaults to `image_type="pano"`, accepting only 360° equirectangular
panoramas. Mapillary 360° panoramas come from systematic fleet mapping campaigns
(TomTom, Bliksurvey, etc.) that follow specific street corridors. Phone/DSLR
contributions are not in this category. Utrecht's 360° coverage under this
filter is therefore sparse.

## Three forward paths

### A. Keep `pano` filter, run full Utrecht
- ~162 cells × ~5 min (many fast-skip on no-pano) ≈ 13 hr
- Risk: may end up with < 50 buildings with imagery; possibly insufficient for
  the ablation.
- Upside: pipeline matches Delft exactly; the Delft-trained InternVL3 fine-tune
  is directly transferable.

### B. Relax to `image_type="both"` (pano + flat)
- Change OpenFacades `prepare_mly_metadata()` `kwarg = {"image_type": "both"}`.
- Risk: flat images have narrow FOV — distribution-shifted vs. Delft training
  data → fine-tuned VLM accuracy likely degrades significantly.
- Upside: image counts likely 10× higher.
- Required: revalidate cropping and AoV math (does `aov_geo` make sense on flat
  images?).

### C. Switch to Google Street View Static API
- Mapillary fail-safe; GSV coverage in NL G3 cities is excellent.
- Risk: $7 / 1000 images, ToS restrictions (no long-term caching, no batch
  download).
- Upside: stable, guaranteed coverage.
- Required: write a GSV downloader, replace OpenFacades stages 2–4.

## Utrecht full run results (completed 2026-05-18)

Decision: option **A** (keep pano filter, full Utrecht).

### Round 1 (162 residential cells, fresh run)
- 41 done / 46 no_pano_coverage / 74 failed / 1 skipped_after_filter
- 2,196 select images
- Mid-run, the local DNS resolver lost `overpass-api.de` → 60+ low-density
  cells failed in a near-identical ~70 s pattern. Not a pipeline bug;
  recoverable on resume.

### Round 2 (resume — retry the 74 attempts=1 failed cells)
- 3 cells recovered to a useful state:
  - `cell_0153` → done (457 images, the single biggest cell)
  - `cell_0173` → done (144 images)
  - `cell_0167` → reclassified as no_pano_coverage
- Most retries failed within 11 s. Signature suggests a Mapillary API
  rate-limit triggered by the burst of metadata queries.
- Final: 44 done / 57 no_pano_coverage / 60 failed (54 of which hit
  attempts=2 and are locked out) / 1 skipped_after_filter

### Final dataset
- 2,206 rows in `merged/individual_building_select.csv`
- **451 unique residential buildings with imagery**
- Coverage: 451 / 20,011 merged residential footprints = **2.25 %**
  (vs. Delft 4.8 %)
- Absolute volume: 2.6× Delft; per-cell density: 0.47× Delft

### Why the per-building coverage rate halved despite more total imagery

Three contributing factors:

1. **Sparser Mapillary 360° distribution.** 49 of 162 residential cells (30%)
   contain zero panos. Delft had no `no_pano_coverage` cells under Patch #5
   semantics.
2. **Lower density inside cells that do have panos.** Per-`done`-cell select
   count is 137 (Delft) vs. 41 (Utrecht). The fleet sweeps that produced the
   panos cover main streets, not the back streets where most residential stock
   sits.
3. **Fixed 600 m cell size vs. variable city compactness.** Delft is compact
   and high-density; 9 done cells cover the bulk of the residential stock.
   Utrecht spreads its 20 k residential pand_ids across 162 cells, many of
   them suburban with a handful of buildings each.

The 60 still-failed cells include some Mapillary-rate-limit victims; a third
retry pass would likely recover a few more but ROI is low (these are all
low-density cells) — leaving them for now.
