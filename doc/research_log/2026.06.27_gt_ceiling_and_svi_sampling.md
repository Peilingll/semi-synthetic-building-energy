# 2026.06.27 — GT ceiling (registry+geometry) and the SVI sampling-bias root cause

## Context

Advisor wants higher F1/accuracy. Investigated (a) how high the GT registry
ceiling can go with extra features, and (b) why the vision-route numbers are low.
Conclusion: the binding limit is a **street-view sampling bias toward old-city
apartments**, not the model.

All LightGBM, fixed HP, class_weight=None, 5-fold StratifiedGroupKFold by pand_id.
Energy label A–G (A+..A++++ merged into A). Leakage columns excluded.

## Feature set used (14 features, identical across all rows below)

- Base attributes: `building_type`, `bouwjaar`, `num_floors`
- TABULA U-values: `u_wall`, `u_roof`, `u_floor`, `u_window`
- Geographic: `city`
- **3D geometry (added today)**: `compactheid` (surface/volume ratio),
  `floor_area_m2` (EP thermal floor area), `shared_ratio` (party-wall fraction),
  `b3_volume_lod22`, `b3_h_max`, `aantal_verblijfsobjecten`

## GT ceiling — same features, different data pool

| Setting | data | n | macro-F1 | κ | acc |
|---|---|---:|---:|---:|---:|
| dev (old-city SVI subset) | dev | 8,051 | 0.284 | 0.399 | 0.391 |
| full 4-city, real distribution | 124k | 124,452 | 0.349 | 0.560 | **0.510** |
| full 4-city, balanced sampling | bal | 26,005 | **0.380** | **0.622** | 0.376 |

- The jump from dev (κ 0.40) to 124k (κ 0.56–0.62) is **NOT from new features** —
  features are identical. It is purely from changing the data pool.
- dev is the *hardest* subset: 88% AB, year clustered ~1920, very homogeneous →
  hard to separate. The full 124k spans suburbs/detached/new builds → easier.
- Balanced sampling raises κ/macro-F1 (removes majority-class inflation) but LOWERS
  acc (0.51→0.38) because there is no large class left to inflate accuracy.
- **Highest by metric**: κ 0.62 (balanced) / acc 0.51 (real dist) / macro-F1 0.38.
- Not yet exhausted: WOZ value + CBS socioeconomic features (Hettinga 2023) could
  push higher toward ~0.71 acc, but those are SVI-invisible and off-topic.

## Root cause: Mapillary street-view sampling bias

building_type distribution (this is the key table):

| | AB (apt) | TH (terraced) | SFH (detached) | MFH |
|---|---:|---:|---:|---:|
| full 124k registry | 54% | 42% | 3.2% | 0.3% |
| **manifest (has street view)** | **88%** | 9.8% | 1.3% | 0.5% |
| dev | 88% | 9.8% | 1.3% | 0.4% |

Absolute counts with street view: AB 8,916 / **TH 992 / SFH 132** / MFH 46
(manifest = 10,086 buildings with GT, 47,238 images, Mapillary `panorama_id`).

- The registry has 42% terraced houses, but only 9.8% of street-view buildings are
  terraced — Mapillary coverage in these 4 cities is heavily skewed to dense
  old-city apartments. Terraced/detached homes largely lack street view.
- dev's 88%-AB is therefore NOT a sampling artefact of the fold split — it is the
  manifest itself. The vision route is locked to this biased ~10k subset.

## Findings

1. **GT ceiling is much higher than the dev number suggested** — κ 0.56–0.62 /
   acc 0.51 on the full 4-city set with 3D geometry, vs κ 0.40 / acc 0.39 on dev.
   But this is the **registry (M1) ceiling**, not the vision system.
2. **The vision route cannot inherit this** — it is bound to the ~10k street-view
   buildings (88% AB), which are the hardest, most homogeneous subset, AND the
   strongest extra feature (compactheid) is SVI-invisible.
3. **The real bottleneck is data sampling, not the method** — Mapillary under-
   covers terraced/detached homes (TH 992, SFH 132). With balanced building types
   the vision classification would likely improve, but the imagery does not exist.
4. **compactheid is the strongest geometry feature but 2D-invisible; shared_ratio
   is 2D-visible (R²=0.46) but weaker downstream** — neither both-strong-and-visible.

## Implications / decisions for advisor

- The low vision-route F1/acc is largely a **street-view sampling limitation**
  (Mapillary old-city bias), defensible as a documented limitation.
- To raise the **registry ceiling** numbers: report the 124k+geometry result
  (acc 0.51 / κ 0.56), optionally add WOZ/CBS (off-SVI). To raise the **vision**
  numbers: would need balanced street-view coverage of TH/SFH — unverified whether
  Mapillary has suburban coverage; re-scraping is high-cost and not guaranteed.
- Open question: is dev 88%-AB because the scrape bbox was city-centre (fixable by
  re-scraping suburbs), or because Mapillary suburban coverage is intrinsically
  sparse (not fixable)? Needs a half-day Mapillary check before any re-scrape.
